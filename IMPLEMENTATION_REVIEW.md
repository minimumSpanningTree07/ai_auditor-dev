# Implementation review and fixes

## Human-in-the-loop workflow

- Human corrections are applied to effective values while `extracted_*` values remain immutable.
- Line-number-based edits take precedence over SKU matching. This is necessary when the SKU itself is the field being corrected; otherwise the correction could be appended as a new line instead of editing the existing line.
- Header fields (invoice number, PO number, currency, date, subtotal, tax, and total) are editable in the Human Review UI and are submitted through the existing revalidation API.
- Data validation now exports the discrepancy set generated by the current validation pass separately. Business validation combines those current data findings with current ERP findings during revalidation, rather than carrying forward stale findings or dropping data-validation findings.
- Persistence uses one outer PostgreSQL transaction. Existing `db.execute`, `db.execute_many`, and `db.fetch_all` calls reuse that transaction connection; failed persistence forces rollback instead of committing a partially-updated invoice snapshot.
- Revalidation preserves discrepancy history and IDs for findings that remain open, reactivates matching findings, inserts newly discovered findings, and marks findings that are no longer produced by current validation as resolved.
- Final audit outcome is based on the current validation results. An explicit human approval is recorded as an override and does not erase open findings; correction/revalidation only approves automatically when current checks pass.

## UI and RAG

- Human Review includes editable header values and line items, alongside the existing invoice-vs-ERP comparison and reviewer feedback controls.
- The current RAG implementation already uses LangChain-compatible components and Qdrant. This revision keeps the existing LiteLLM/provider setup and does not add a second framework or duplicate indexing path.
- The current Streamlit styling is preserved rather than replacing the application or changing deployment configuration.

## Validation limits

Python compilation, selected tests, Compose YAML parsing, and shell syntax checks were run where the local environment had dependencies available. This execution environment does not include the complete runtime dependency set (including `langgraph`, `litellm`, and `psycopg2`), so a full test collection and live PostgreSQL/Qdrant/ERP integration test could not be completed here. Run the full suite in the project's Docker environment before production use.

## RAG evaluation addition

Added an optional Ragas 0.2.15 evaluation runner at `agent/rag/evaluate.py`, using the existing Qdrant retrieval and LiteLLM generation path. It reports Faithfulness, Response Relevancy, Context Precision, and Context Recall, writing per-case CSV and aggregate JSON outputs. The starter JSONL file is `agent/rag/evaluation_dataset.jsonl`; replace its reference templates with verified gold answers before treating the scores as a meaningful benchmark. Evaluation requires model credentials, a populated Qdrant collection, network/provider access, and rebuilding the agent image to install the optional dependencies. It was not run end-to-end in this environment.
